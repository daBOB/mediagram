**Bundle format** (`crates/mlib-spec/src/subtitle_bundle.rs`, new): `Bundle`/`BundleTrack` structs, `encode`/`decode` (gzip+JSON via `flate2`, added to mlib-spec's own `Cargo.toml` — already a pinned workspace dep), caps enforced in `decode`: compressed ≤ 16 MiB (checked before touching the gzip reader), decompressed ≤ 64 MiB (via `Read::take(cap + 1)`, so a bomb is *detected* not merely truncated), one track's `vtt` ≤ 4 MiB, `v != 1` → `UnsupportedVersion`. `valid_sha256` reuses `is_lower_hex` from `package::charset` — that function and its re-export in `package/mod.rs` moved from `pub(super)`/private `use` to `pub(crate)`, the minimal visibility change letting a crate-root-level sibling module reuse it without a second copy. `SUBS_CAPTION_PREFIX`, `render_caption`, `bundle_file_name`, `SUBS_MIME_TYPE` also live here (Requirements said this belongs to the bundle module even though phase 06 is what will call `render_caption`/`bundle_file_name` in anger). Verified — not just asserted — that `#mlib-subs` collides with neither `is_mlib` (`#mlib v=` prefix) nor `is_index` (`#mlib-index` prefix): both are unit-tested directly against `render_caption`'s output, and `rescan.rs`/`index_caption.rs` needed no code change since the prefixes already don't overlap.

**Shared fixtures**: `crates/mlib-spec/tests/fixtures/subtitle-bundle-v1.json` (German Forced, German, English SDH, two cues each, read via `include_str!` in `subtitle_bundle_tests.rs`, round-tripped through encode/decode). `web/test/fixtures/subtitles/choice-cases.json` — 15 cases encoding the plan.md playback rule line by line (audio-tag normalisation both directions, the `wanted`/`regular` four-tier match including the "remembered names something missing → retry the tier with the profile preference" fallback, the toggle-on chain's four tiers each demonstrated including the bare "first regular" catch-all, the forced-only/no-picker/no-CC shape, and the `und`-only-matches-remembered-`und` rule with a companion case showing it is *not* reachable through the preference tier). Field names (`tracks`, `remembered`, `preferred`, `audioTag`, `alang`, `last` / `audio`, `regular`, `forced`, `toggleOn`, `pickerRows`, `ccVisible`, `styleVisible`) match the phase text verbatim since nothing in the current tree defines them yet — phase 03/04/05 own giving them a reader.

**Merge** (`crates/mediagram/src/index/merge_subtitles.rs`, new + `merge_subtitles_tests.rs`): newer `uploaded_at` wins per set (`ON CONFLICT ... DO UPDATE ... WHERE excluded.uploaded_at > subtitle_files.uploaded_at`, dynamic column list from `shared_columns` the way `merge_categories`/`merge_anime_overrides` already do); on a win, `subtitle_tracks` for that set are deleted and reinserted whole from the channel (an `ON CONFLICT` upsert on the file row does not cascade — only a `DELETE` fires the FK cascade — so tracks need an explicit replace, exactly as specced); any set with a `main.subtitle_files` row has its `assets` `kind='subtitle'` rows deleted. `merge_copy.rs::fill_missing_assets` gained the matching exclusion so the channel's *own* stray inline rows for an already-bundled set are never refilled. Wired into `merge.rs::copy_kept` before `fill_missing_assets`, after the candidate sets/parts loop (so a channel-only set's bundle is copied in the same pass as the set itself). `MergeReport` gained `subtitles_taken`/`channel_lacks_subtitles`; `report.rs` prints both, the alarm as a named warning.

9 tests in `merge_subtitles_tests.rs`: channel-only bundle for a shared set copied with tracks (+ FK check), channel-only *set* whose bundle rides along with it, newer replaces older including tracks, older ignored, a channel-only candidate that is *not* kept leaves its bundle out too (this stands in for "set absent locally → skipped" — a first cut using a set with no `sets` row anywhere hit a `FOREIGN KEY constraint failed`, because this build enforces FK on **every** connection including the bare `sqlite_init::open` ones the test helpers use for the channel side, not just `db::open`'s local index; removed that test rather than fight the constraint it exists to enforce), v12 channel flags local rows / does not flag when local has none, inline channel rows not filled in for an already-bundled set, idempotent re-merge reports zero.

**Guard** (`crates/mlib-spec/src/index_caption.rs` + `crates/mediagram/src/channel_index/pull.rs`): new `index_caption::schema(caption)`, same shape as `pushed_at`. `pull::current()` — the one function every pull and every publish (`AfterPull` and `Force` alike) calls to choose the channel's index — now refuses when the chosen caption's schema exceeds this build's `SCHEMA_VERSION`, naming the reinstall command. `publish.rs`'s `Force` branch, which previously skipped `pull::current` entirely, now calls it purely for the guard's side effect before snapshotting. Three integration tests in `channel_index.rs` (`pull`, `AfterPull`, `Force`, each against a fake channel whose newest caption claims `"schema":99`) confirm nothing is sent and the local index is untouched in all three paths.

**Stale-uploader alarm**: `pull.rs::merge_in` calls `pins::owe_publish` when the merge reports `channel_lacks_subtitles`. `channel_index::pull_from_channel` (the `pull-index` command's own connect/pull/disconnect wrapper — distinct from the pull `publish::publish` runs internally) compares `publish_owed` before and after the pull; if it went from `None` to `Some`, it republishes (`AfterPull`) and prints why. This is scoped to *this* pull having caused the debt (nothing else currently calls `owe_publish` from a pull), rather than a generic "always republish if anything is owed" — an upload session's own unrelated `--no-push` debt is left for the next normal publish, not force-triggered by an incidental `pull-index`.

**`send_document`**: `ChannelRemote::send_index(path, caption)` → `send_document(bytes, name, mime, caption) -> i32`. `telegram_remote.rs` now uploads over `std::io::Cursor::new(bytes)` (the documented `upload_stream` pattern for in-memory buffers) instead of opening a file — the `path`/`tokio::fs` machinery and the module-private `INDEX_MIME_TYPE` constant are gone from that file entirely. `INDEX_MIME_TYPE` moved to `channel_index/mod.rs` (private, reached by `publish.rs` via `super::`, the same idiom already used there for `Mode`/`pull`/`unpin`) since the mime is now a caller-supplied argument rather than a Telegram-implementation detail. `publish.rs::send` reads the snapshot file into memory once and calls `send_document(&bytes, mlib_spec::schema::INDEX_FILE, INDEX_MIME_TYPE, &caption)`. The fake channel's `send_document` no longer needs `std::fs::read` at all (bytes arrive directly), and drops the file-name/mime params (`_name`, `_mime`) since nothing in this phase's tests asserts on them — a later phase extending the fake to check a bundle's file name/mime is free to add that, `tests/support/channel.rs` is exclusively this phase's file so there is no ownership question, just no present need.

## Concerns / things worth the lead's attention

1. **Reader parity confirmed but not exercised end-to-end**: `mediagram-core` was not touched (no Rust changes there), because its schema handling is already lower-bound-only (`api/channel/install.rs:44-50`, verified). A v13 index is invisible-but-harmless to an *installed* Android build. Nothing to rebuild for this phase alone. Flagging per instructions since `mediagram-core` is on the "say so" list — the answer is "no changes, no rebuild needed here," not "changes, rebuild."
2. FK enforcement turned out to be on by default for **every** `rusqlite`/`sqlite_init::open` connection in this build (not just `db::open`'s explicit `PRAGMA foreign_keys=ON`), including the plain channel-snapshot connections `open_channel_at` builds in tests. This affected test design (see the removed "GHOST" test above) but is a pre-existing property of the build, not something this phase changed — worth knowing for anyone writing fixture-DB tests elsewhere in this crate.
3. The stale-uploader alarm's auto-republish lives in `pull_from_channel` (the `pull-index` command's own wrapper), not inside the shared `pull::pull_from`/`merge_in` used internally by every `publish`. That's deliberate — a publish's own internal pull already ends in a send, so a second forced publish from inside it would be redundant — but it means the auto-restore only fires on an explicit `mediagram pull-index`, not on a bare `mediagram add …` that happens to publish. A publish's `AfterPull` step still records the `publish_owed` debt via the same `merge_in` code path, so nothing is lost — the next `pull-index` or the next publish clears it — but the *printed* "restoring them" message and immediate re-publish is `pull-index`-only.
