# Phase 02 core search — review fixes

Findings tally as relayed by the coordinator: 1 High, 2 Medium, 5 Low. This
report details H1, M1, M2, L1, L2, L3, L5 (the seven with substance passed
along); a fifth Low was counted but not detailed in the relay — see "Open
question" at the end rather than guessing at its content.

## H1 — title tie-break disagreed with the web's `localeCompare("de")`

`search/rank.rs` tied same-field hits by `fold(title)` then raw title. Real
library titles disagreed with the web on real pairs: leading punctuation,
a percent sign beside a plain number, case. Probed against
`~/.local/share/mediagram/library.db` (903 sets, 162 summaries) over 467
queries sampled from real titles: 0 mismatches after the fix, versus a
failure on the very first tie-break pair with the old comparator (verified
directly — reverted to the fold-based comparator, `cargo test --test
shared_search_fixtures` failed on `"tie-break: a plain number outranks a
percent sign at the same value"`, restored, passed again).

**Fix.** Added `icu_collator`/`icu_locale_core` (`compiled_data` feature,
CLDR German tailoring baked into the binary, no runtime data file).
`rank::collator()` builds a `CollatorBorrowed` once per `search()` call;
`compare()` replaces the folded-string tie-break. All 6 pairs the review
named checked directly against the collator before wiring it in.

## M1 — the shared fixture didn't cover the tie-breaks

`cases.json` had 11 cases, none exercising a same-field tie on two distinct
titles. Extended to 31: the 6 real pairs above, punctuation-leading titles
mixed with a plain one, duplicate titles (stability), a null title, a
show-field hit, a chap-field hit, ß/ss and capital ẞ, empty/whitespace/
punctuation-only queries, three excerpt-window edges (match at the very
start, at the very end, and a cut that lands beside multi-byte `ü`
characters), and a decomposed-`Übersicht` summary proving a title match
still wins and nothing panics on already-decomposed input. Every new case's
`expect` was generated by running the web's own `SearchIndex`, not
hand-computed. `bun test` and `cargo test` both pass all 31.

## M2 — folding the corpus on every call cost too much

Measured on the real library: ~18ms/call per the coordinator's report,
reproduced here as ~25ms/call cold (fold + rank) versus ~0.4ms warm.
Likely over the phase's 50ms tablet budget.

**Fix.** `search::rank::Corpus` separates folding (`Corpus::build`, once)
from ranking (`search`, every call). `api::search::cache::SearchCache`
caches the built `Corpus` in `Core`, keyed by the catalog's *resolved*
version directory (`std::fs::canonicalize` of the `current` symlink's
target, not the symlink's own unchanging path) — a refresh changes the
resolved path and invalidates the cache the way the web's process-lifetime
fold is invalidated by nothing, because its catalog never changes under
it. Added `api/search/cache_tests.rs`: same version reuses the `Arc`
(`Arc::ptr_eq`), a changed version rebuilds it.

## L1 — `flatten` used the wrong Unicode properties

Approximated `\p{Diacritic}` with "is this an NFD combining mark", and
`\p{Letter}`/`\p{Number}` with Rust's `char::is_alphanumeric` (the broader
derived `Alphabetic` property). Both diverged from the web:
`fold("Geht´s")` gave `"geht s"` here versus `"gehts"` on the web (a
standalone acute accent, not a combining mark, was space-separated instead
of dropped); `"Ⓐ"` would have stayed a letter instead of collapsing to
nothing (circled compatibility letters are `So`, not `L`, under strict
General Category).

**Fix.** Replaced with the same two regexes the web uses:
`\p{Diacritic}` (drop), then `[^\p{L}\p{N}]+` (space). Added
`fold("ʼn") == "n"`, `fold("Ⓐ") == ""`, `fold("eͣx") == "e x"` to both
`normalize_tests.rs` and `web/test/search-normalize.test.ts` — the last one
a combining mark the web's own `\p{Diacritic}` does *not* cover, so it
still splits the word; reproduced faithfully rather than smoothed over,
since the port's job is to agree with the web, not to improve on it.

## L2 — excerpt padding counts `char`s, the web counts UTF-16 units

Accepted as a deliberate difference, not fixed: the two agree for BMP text
(everything this library's summaries are written in) and only disagree if
a surrogate pair sits exactly on the window edge, where the web's UTF-16
count splits it — a web defect, not a decision worth porting. Documented
in `phase-02-core-search.md`'s Key insights. The "cut beside multi-byte
characters" fixture case (M1) uses `ü` deliberately, not an emoji, because
that stays inside where the two implementations agree.

## L3 — comments and the changelog claimed "no ICU"

`search/rank.rs`, `search/mod.rs`, `shared_search_fixtures.rs`'s module
docs, and the changelog entry all said Rust has no ICU `localeCompare` and
falls back to a folded-string tie-break. False as of H1. All four rewritten
to describe `icu_collator` instead.

## L5 — the shared-fixture test skipped silently on a missing fixture

`shared_search_fixtures.rs` treated a missing `cases.json` the same as an
absent `web/` checkout: print and return, no failure. Inside this repo
`web/` is never absent, so a missing fixture there is the pairing broken,
not a deliberate accommodation — and skipping hid exactly the drift this
file exists to catch.

**Fix.** `load()` now checks whether `web/` itself exists first; only then
does it skip. If `web/` is present but `cases.json` is not, it panics.
Verified by moving the file aside: test failed with a clear message
naming both paths; restored, passed again.
