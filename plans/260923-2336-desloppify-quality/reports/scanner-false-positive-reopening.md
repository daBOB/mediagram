# Scanner false-positive reopening

Date: 2026-09-24
Status: DONE — intentional upstream policy; supported persistent workflow verified.

## Finding

`plan skip --false-positive` does not permanently suppress a detector result. A subsequent scan deliberately reopens the finding if the detector still emits it. The maintainer introduced this policy in [commit 79f9fa2](https://github.com/peteromallet/desloppify/commit/79f9fa2f1fc4d214cd5e590e0524f18e1abd50b5) and explicitly confirmed it in [PR #363](https://github.com/peteromallet/desloppify/pull/363#issuecomment-4027074397). Its stated purpose is preventing scan-proof score inflation from false-positive resolutions.

The installed tool and upstream HEAD `3a7735d531a96b6a226bfbdc9fd662b14195f857` both implement this behavior. In `desloppify/engine/_state/merge_issues.py:274–295`, a re-detected `false_positive` becomes open, increments `reopen_count`, removes the resolution attestation, and replaces the note. This explains the six original excluded-directory findings in `.desloppify/state-rust.json`. The original evidence remains available in `.desloppify/plan.json` execution history.

Plan reconciliation can subsequently restore a skipped status while pruning the skip, leaving a `false_positive` status alongside a reopened note and no resolution timestamp. The isolated CLI reproduction observed this too. Existing [issue #759](https://github.com/peteromallet/desloppify/issues/759) already tracks the related scan-output/final-state discrepancy. No duplicate issue or unsolicited policy change was published.

## Supported persistent workflow

Use the official `suppress` command for each independently adjudicated finding, preserving its concrete evidence in the attestation. Its CLI help explicitly describes permanent suppression for false positives and accepted debt (`app/cli_support/parser_groups.py:331–351`). Keep legitimate directory exclusions in place.

For example, from the repository root, with the normal project tool command:

```sh
desloppify --lang rust suppress \
  'stale_exclude::web/node_modules::web/node_modules*' \
  --attest 'I have actually reviewed this exclusion: web/node_modules contains installed Bun/npm dependencies, not authored application source; Rust imports cannot establish its purpose. I am not gaming the score by hiding a real defect.'
```

Use the existing combined tool wrapper in place of `desloppify` if that is the controller's current executable. Then continue the normal queue/scan workflow. The investigation did not apply this command to project state.

The trailing `*` is intentional and supported glob syntax. A bare full issue ID currently captures a path-independent fingerprint (`app/commands/suppress.py:60–73`). That fingerprint may also suppress an equivalent finding in another file. The full-ID glob takes the explicit ID matching branch and avoids fingerprint capture/fallback (`engine/_state/filtering.py:174–196`). It fixes the detector, file and rule prefix; it is not a detector-wide or directory-wide suppression. Read-only matching against the current Rust state confirmed every candidate below matches only its own existing issue.

For the six original directory findings, use these patterns with the corresponding evidence already recorded by the controller:

| Pattern | Recorded evidence to retain in the attestation |
| --- | --- |
| `stale_exclude::.agents::.agents*` | Locally installed workflow skill documents and tooling state, explicitly ignored. |
| `stale_exclude::.claude::.claude*` | Local skills, memory and nested worktrees; including them duplicates source and scans tool state. |
| `stale_exclude::.gstack::.gstack*` | Generated browser audit JSONL and console/network logs, already ignored. |
| `stale_exclude::android/core/rust/src/main/kotlin/uniffi::android/core/rust/src/main/kotlin/uniffi*` | Generated UniFFI bindings rebuilt by `scripts/generate-android-bindings.sh`; authored Android source is assessed separately. |
| `stale_exclude::graphify-out::graphify-out*` | Generated graph, cache and derived reports, identified as generated by `.gitignore`. |
| `stale_exclude::web/node_modules::web/node_modules*` | Installed dependencies rather than repository-owned implementation. |

The same mechanism technically applies to the seven Rust coverage findings, but the controller elected to retain their strict penalties and document the behavioral test evidence instead. No code-finding suppression is recommended or requested. Two further generated-image-directory findings were present; they also remain untouched.

This is an explicit permanent detector suppression, not a code repair. The tool records the full attestation and pattern in `attestation_log`, and reports suppression counts/percentage in scan history. Suppressed findings are excluded from scoring, including verified scoring. Report them honestly as evidence-supported adjudications; do not describe the resulting score as additional code fixes. Revisit each suppression when the relevant tests, implementation or directory purpose changes. Do not blanket-suppress `test_coverage::*` or remove valid exclusions merely to eliminate warnings.

## Verification

All tool experiments ran in a new isolated upstream checkout: `/tmp/desloppify-false-positive-fix-U94uNV`. Its nested `scratch/repro` Git repository had only a two-line Python function and two excluded generated-capture directories. The real CLI created its config/state through commands; no scanner state was hand-edited.

1. Real initial scan emitted both `stale_exclude` findings.
2. `plan skip --false-positive` with evidence followed by a scan printed one reopened finding and incremented its reopen count to one. Plan reconciliation left the reopened note and removed the original skip.
3. `suppress 'stale_exclude::.tooling::.tooling*' --attest ...` followed by **two real scans** retained suppression and its full audit entry. The reopen count stayed at one. The other directory's finding remained open and unsuppressed.
4. The final scan history recorded `ignored: 1`, `raw_issues: 22`, `suppressed_pct: 4.5`, and `ignore_patterns: 1`; config captured no broad fingerprints.
5. Read-only matching against current project Rust state confirmed all 15 candidate full-ID glob patterns matched exactly one existing finding each.

The fixture scans used `--skip-slow --no-badge`. Follow-up fixture scans used the documented `--force-rescan` attestation to reproduce the interaction without resolving unrelated fixture review prompts; this bypass was never used on project state. `next` ran after each fixture scan. The installed Python environment lacked Bandit, so scans reported reduced security coverage; stale-exclusion detection and suppression still ran normally.
