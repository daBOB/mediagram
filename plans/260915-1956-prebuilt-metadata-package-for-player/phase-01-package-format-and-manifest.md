# Phase 1: Package format and manifest

## Overview
Define the package as a format before any code writes one: the archive
layout, the manifest inside it, the plaintext pointer beside it, and the
rule that binds the two together cryptographically.

## Key insight
The pointer is published in the clear and an attacker can rewrite it. The
only defence that survives that is making the pointer's identifying fields
the **associated data** of the AEAD. Then a replayed archive under an edited
pointer fails its authentication tag, because the tag was computed over
those exact bytes. Without this, a rollback guard that reads `created_at`
from the pointer is guarding with a value the attacker supplies.

## Requirements
- Functional: typed manifest and pointer structures with a stable field
  order; a canonical byte serialization of the pointer's identifying fields
  for use as associated data; validated poster keys.
- Non-functional: the pointer reveals nothing about the library's contents.

## Architecture

Inside the archive:

```json
{
  "format": 1,
  "created_at": 1781827200,
  "schema": 1,
  "spec": 2,
  "sets": 312,
  "parts": 468,
  "posters": [
    {"key": "tmdb-movie-693134", "file": "posters/tmdb-movie-693134.jpg"}
  ]
}
```

Beside the archive, at a fixed URL, `latest.json`:

```json
{
  "format": 1,
  "created_at": 1781827200,
  "file": "prebuilt_mediagram_db_20260616-3d7e10c4.tar.gz.enc",
  "url": "https://example.com/prebuilt_mediagram_db_20260616-3d7e10c4.tar.gz.enc",
  "bytes": 8127744,
  "sha256": "…of the encrypted file…",
  "cipher": "aes-256-gcm",
  "key_id": "9f2c41ab",
  "schema": 1,
  "spec": 2
}
```

`schema` and `spec` above are the values in the tree today
(`SCHEMA_VERSION = 1`, `SPEC_VERSION = 2`). They are read from the constants
at runtime, never hard-coded; the tutorial work will move them and the
examples must follow. Every example in the eventual specification is
generated by a test rather than typed by hand.

**Associated data.** The bytes authenticated alongside the ciphertext are the
canonical serialization of `format`, `created_at`, `key_id`, `schema` and
`spec`, in that order, as a minified JSON object. The reader reconstructs
them from the pointer it fetched and passes them to the cipher. Editing any
of those five fields in transit makes decryption fail.

**Poster keys.** `tmdb-movie-{id}` and `tmdb-tv-{id}`. TMDB's movie and
television id spaces are independent, so a key without the kind would let
movie 550 and show 550 collide onto one poster. A key must match
`^[a-z]+-[a-z]+-[0-9]+$` before it is used in a path; anything else is
skipped with a warning. That check is defensive rather than load-bearing
here, because ids come from an integer column, but the same helper protects
any future key whose input is less trustworthy.

**File naming.** `prebuilt_mediagram_db_YYYYMMDD-{first 4 bytes of the
ciphertext sha256}.tar.gz.enc`. Stateless and collision-free, with no
counter that depends on what happens to be in a local directory.

## Related Code Files
- Create: `crates/mlib-spec/src/package.rs` (`PackageManifest`,
  `PosterEntry`, `LatestPointer`, `PACKAGE_FORMAT`, `associated_data`,
  `poster_key_is_valid`, file-naming helper)
- Modify: `crates/mlib-spec/src/lib.rs` (export the module)

## Implementation Steps
1. Define the structures above with `serde`, field order fixed as written,
   and `PACKAGE_FORMAT: u32 = 1`.
2. Implement `associated_data(&LatestPointer) -> Vec<u8>` as minified JSON
   over exactly the five identifying fields, and test that changing any one
   of them changes the output.
3. Implement `key_id(key: &[u8; 32]) -> String` over sha256, first four
   bytes, hex.
4. Implement the file-naming helper and `poster_key_is_valid`.
5. Implement the reader-side compatibility check on the pointer: known
   `format`, and a `schema` the reader supports.
6. Round-trip tests, plus a test asserting the pointer serializes with no
   field naming a title, set, chat or message.

## Success Criteria
- [ ] Manifest and pointer round-trip byte-identically
- [ ] Associated data changes when any identifying field changes, and not otherwise
- [ ] `key_id` is stable for a key and differs for a different key
- [ ] Poster keys containing a path separator, `..`, or a control character are rejected
- [ ] A pointer with an unknown `format` is rejected by the compatibility check
- [ ] A test proves the pointer contains no library content
- [ ] `schema` and `spec` are read from the crate constants, not literals

## Risk Assessment
- Publishing anything descriptive in the clear undoes the encryption
  decision. Mitigation: the pointer's fields are enumerated here and a test
  fails if that set grows.
- Associated data is easy to get subtly wrong, for instance by serializing a
  map whose key order varies. Mitigation: it is a fixed-order struct, not a
  map, and a test pins the exact bytes.
