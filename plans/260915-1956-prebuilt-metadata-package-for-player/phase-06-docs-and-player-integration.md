# Phase 6: Docs and player integration notes

## Overview
Write the normative package specification and the notes a player author
needs, so the Android client can be written against a document rather than
against this repository's Rust code.

## Requirements
- Functional: a specification complete enough to implement a reader without
  reading Rust; the operator-facing setup documented in the README; the
  roadmap and changelog updated as the documentation rules require.
- Non-functional: examples in the spec come from a test fixture, so they
  cannot drift from what the code emits.

## Architecture
```
docs/mlib-package-v1.md      normative: layout, manifest, latest.json,
                             cipher framing, versioning, reader algorithm
docs/system-architecture.md  add the export path to the data flow
README.md                    operator setup: key, publish_cmd, first export
docs/development-roadmap.md  package as a delivered capability
docs/project-changelog.md    dated entry
```

## Reader algorithm, as the spec will state it
1. Fetch `{base}/latest.json`. Reject it if `format` is a version the
   reader does not know.
2. Refuse a pointer whose `created_at` is older than the package already
   held. This is the rollback guard: a stale cache or a hostile file server
   must not be able to walk a player backwards.
3. Compare `key_id` against the held key and stop here on a mismatch, so a
   wrong key costs one small request rather than a full download.
4. Compare `file` against what is already cached; identical means nothing
   to do.
5. Download the named archive and verify its sha256 against the pointer,
   refusing the file on mismatch.
6. Decrypt with `Cipher.doFinal` over the whole ciphertext. **Never through
   `CipherInputStream`**: on Android it swallows `AEADBadTagException` and
   yields truncated plaintext instead of failing, which would silently
   accept tampered data. A failure here means a wrong key or a corrupt
   file and must be reported, not retried.
7. Unpack, read `manifest.json`, and confirm `schema` is a database layout
   the reader supports.
8. Open `library.db` read-only. Use `PLAYABLE_SQL` to list what is
   playable, then stream parts through Telegram by `(chat_id, message_id)`.

## Implementation Steps
1. Write `docs/mlib-package-v1.md`: archive layout, manifest schema with
   every field typed, `latest.json` schema, cipher and framing exactly as
   implemented, versioning rules for `format`, `schema` and `spec`, and the
   reader algorithm above.
2. State the security model plainly: the archive holds the private channel
   id and every message id; the key is the only thing protecting it; the
   hosting URL is not a secret and must not be treated as one.
3. Document key generation and how to transcribe the key into the player.
4. Update the architecture doc's data flow to include the export path, and
   note that the pinned Telegram index remains the recovery copy.
5. README: generate a key, set `publish_cmd`, run the first export, verify
   by decrypting by hand with the documented command.
6. Roadmap and changelog entries per the documentation rules.

## Success Criteria
- [ ] Someone can implement a reader from the spec alone, with no Rust
- [ ] Every manifest and pointer example in the doc is generated by a test that asserts equality with real output
- [ ] The documented hand-decryption command works against a real package
- [ ] Security model section states what a leaked URL does and does not expose
- [ ] The `CipherInputStream` warning and the rollback guard appear in the reader algorithm, not only in prose
- [ ] Docs stay within the 800-line guidance per file

## Risk Assessment
- A specification that drifts from the code is worse than none, because a
  player author trusts it. Mitigation: examples are fixture-generated and
  asserted, the pattern already used for the caption spec.
- Documenting the cipher framing invites scrutiny, which is the point. Any
  reviewer finding a flaw here is cheaper than a player author finding it
  after release.
