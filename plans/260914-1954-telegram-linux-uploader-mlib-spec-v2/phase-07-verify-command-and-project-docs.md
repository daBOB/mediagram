# Phase 7: Verify command and project docs

## Overview
Add `verify` (metadata check by default, `--full` re-download + hash), write the normative spec document and the project docs required by the documentation rules, and run the end-to-end acceptance checklist.

## Requirements
- Functional: `verify <set-id>|--all`: default checks invariant, fetches each part's message by id, compares document size to `byte_length`; `--full` streams each part via grammers `iter_download`, hashes, compares to `parts.sha256`, sets `parts.verified_at`; resumable (skips parts verified after `--since`).
- Non-functional: `--full` bandwidth warning with total bytes before starting; exit code non-zero on any mismatch.

## Architecture
```
crates/mediagram/src/commands/verify.rs   # orchestrates checks, prints table
crates/mediagram/src/verify/download_hash.rs # client.iter_download(&document) (Document implements the Downloadable trait) → Sha256
docs/mlib-spec-v2.md            # normative caption + index + part naming spec, examples, invariants, versioning rules
docs/system-architecture.md     # crates, data flow add→channel→index, state model, DR path
docs/code-standards.md          # module layout, <200-line rule, error handling (anyhow at CLI edge, thiserror in libs), testing tiers (unit / fixture / live-ignored)
docs/development-roadmap.md     # v1 done items, TV app round as next
docs/project-changelog.md
README.md                       # install, config.example.toml, login, add, resume, verify, rescan
```

## Implementation Steps

4. Write remaining docs and README.

6. `cargo clippy --all-targets -- -D warnings`, `cargo fmt --check`, line-count check script for the 200-line rule.

## Success Criteria
- [ ] `verify --full` on a 3-part set reports 3/3 hash matches — pending live gate (needs a real Telegram channel + session; see Completion notes for the unit-level equivalent)
- [ ] Tampered `parts.sha256` row → verify exits non-zero and names the part — pending live gate (same; `report::apply_hash` hash-mismatch path is unit-tested in isolation)
- [x] `docs/mlib-spec-v2.md` is sufficient for someone to write a parser without reading Rust
- [ ] Whole-plan acceptance checklist passes and is recorded in the changelog — pending live gate (needs `tmdb_key` + a real channel; see `plan.md` → "Open live gates" in `docs/development-roadmap.md`)

## Risk Assessment
- `--full` on a 60 GB set is slow and download-throttled → default mode is metadata-only; warn with byte total.
- Docs drift from code → spec examples are generated by a test that writes them to `docs/examples/` and asserts equality.

## Completion notes (2026-09-15)

Implemented by a worktree agent; no live Telegram/TMDB credentials were
available in this environment, so everything below was validated without
network access.

**Code** (file ownership: `commands/verify.rs`, `verify/{mod,report,download_hash}.rs`, `tests/verify_report.rs`):
- `verify::report` is the pure decision layer (`ExpectedPart`,
  `ObservedMessage`, `PartVerdict`, `SetReport`, `verify_size`,
  `apply_hash`, `check_local_invariant`, `render_rows`, `summary_line`) —
  no IO, fully unit-tested in `tests/verify_report.rs` (11 tests: size
  mismatch, missing message, no-document, doc-id-changed warning,
  hash match/mismatch, hash skipped after a size failure, local invariant
  row-count/sum mismatches, mixed-result and all-ok summaries).
- `verify::download_hash` is the only Telegram-facing half: batched
  `get_messages_by_id` (100 ids/call, `with_retry` since it's a plain
  read) and `hash_document` (chunked `iter_download` straight into
  `Sha256`, never buffering a whole part). Deliberately has **no** retry
  around `iter_download().next()`: read `files.rs` in the vendored
  grammers-client 0.10 source and confirmed `DownloadIter::next` silently
  ends the stream after any failed chunk request instead of resuming it —
  retrying there would produce a wrong, truncated hash instead of a loud
  error, so a transient failure surfaces as an error and the caller
  re-runs `verify --full` for that part.
- `commands/verify.rs` orchestrates: resolves `set_id`/`--all` (bails if
  neither given), loads local part rows, prints the `--full` byte/part
  cost up front, fetches messages, builds a `PartVerdict` per part
  (immediate `NotUploaded` failure for any part not locally `done`, no
  Telegram call needed), streams+hashes and writes `parts.verified_at`
  when `--full`, prints `report::render_rows`/`summary_line` per set, and
  returns `Err` (non-zero exit) if any set failed.
- `verify` was added to `src/lib.rs` per the allowed exception; no other
  file outside the listed ownership was touched.
- All new files are under the 200-line limit (`commands/verify.rs` 186,
  `verify/mod.rs` 76, `verify/report.rs` 198, `verify/download_hash.rs`
  67, `tests/verify_report.rs` 184).
